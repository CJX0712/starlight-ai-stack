# ADR-006: 答案落地校验与内存守卫修正

- 状态：Accepted（2026-09-20）
- 作者：晨星

跑通基础链路后，用 7B 档实测暴露了两个"提示词管不住"的问题，都改为确定性代码校验。

## 问题一：模型擅自编造缩写全称

资料原文只写「两路结果通过 RRF 融合排序」。qwen2.5:7B 的回答补成：

> 两路结果通过 RRF（Relevance Function Fusion）融合排序。

括号里的全称是编造的（正确应为 Reciprocal Rank Fusion），资料里从未出现。有意思的是 qwen3:4B 不会犯这个错——模型更大反而更爱"补全"。

**先试提示词**：在 system prompt 加硬约束「不得补充资料中未出现的信息，缩写照原样使用」，并给出 RRF 的例子。**实测无效**，7B 照编不误。

**改为确定性校验** `AnswerGenerator.enforce_grounding`：

1. 正则匹配「大写缩写 + 括号展开」结构
2. 若缩写本身不在检索到的资料里，原样放行（不越权处理）
3. 若缩写出现在资料里，则把括号展开的每个英文词拿去资料中核对
4. 核对不上 → 整段删掉，只留缩写本身

代价：即使模型给出的是**正确**的全称，只要资料没写也会被删。这是有意为之——本系统的第一原则是「可追溯」，宁少说不多说。

## 问题二：内存守卫把"已加载"误判成"内存不足"

7B 档上线后出现诡异现象：模型明明在，却总被降级。原因是 7B 权重常驻内存后，**系统可用内存自然降到 1–2GB**，而守卫只读可用内存，于是把「模型已加载的结果」当成「内存不足以加载模型的风险」。

**修正**：守卫先查 Ollama `/api/ps` 拿到已常驻模型列表；要用的模型已在内存里 → 跳过内存阈值判定，只记录一条说明。阈值本身也按实测从 4.0GB 下调到 3.0GB（实测可用 3.9GB 时 7B 稳定跑 2.92 tok/s）。

## 后果

- 正面：两条都是"不依赖模型自觉"的机械保障，可被单元测试锁死
- 反面：遇到确需补充缩写全称的场景会有轻微信息损失，可接受
- 防护：`tests/test_config.py`（4 例）与 `tests/test_generator.py`（2 例）覆盖上述决策
